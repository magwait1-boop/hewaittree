# تفعيل رسائل الزوار الخاصة

حُضّر الترحيل داخل المشروع، ولم يُنفّذ على قاعدة البيانات المستضافة لأن اتصال Supabase الحالي لم يُظهر أي مشروع مخوّل. يتطلب التفعيل الخطوات التالية في **مشروع Supabase نفسه الذي يستخدمه الموقع**.

1. افتح **SQL Editor** وشغّل كامل الملف `supabase/migrations/20261012112043_private_visitor_feedback.sql` مرة واحدة. ينشئ جدول `visitor_feedback` للرسائل وجدول `feedback_admins` لقائمة المسؤولين، ويضبط الصلاحيات وRLS. يمكن أيضًا تطبيق الترحيل ضمن آلية نشر الترحيلات المعتادة بعد ربط المشروع الصحيح؛ لا تطبّق الترحيلات القديمة عشوائيًا على قاعدة بيانات موجودة.
2. من **Authentication → Users → Add user** أنشئ حسابًا للمسؤول ببريد إلكتروني وكلمة مرور قوية. تأكد من تأكيد البريد إذا كان إعداد المشروع يطلب ذلك. يمكن استخدام حساب Supabase Auth موجود يخص المسؤول. لا تستخدم كلمات المرور التجريبية القديمة للشجرة.
3. انسخ **UUID** الخاص بالحساب، ثم نفّذ في SQL Editor بعد استبدال النص التالي بمعرّف الحساب الحقيقي:

   ```sql
   INSERT INTO public.feedback_admins (user_id)
   VALUES ('ضع-هنا-معرف-حساب-المسؤول-UUID')
   ON CONFLICT (user_id) DO NOTHING;
   ```

4. تأكد من تفعيل تسجيل الدخول بالبريد وكلمة المرور في **Authentication → Sign In / Providers → Email**. لا يحتاج الزوار إلى إنشاء حساب. تستخدم الواجهة متغيرَي `NEXT_PUBLIC_SUPABASE_URL` و`NEXT_PUBLIC_SUPABASE_ANON_KEY` الموجودين أصلًا؛ لا تحتاج هذه الميزة إلى `service_role` أو أي مفتاح سري في الواجهة.
5. افتح زر **«تقديم مقترح أو تعليق»** وأرسل رسالة اختبار. افتح **«رسائل الزوار»** أو المسار `/visitor-messages` وسجّل الدخول بالبريد وكلمة مرور حساب المسؤول أعلاه. تظهر الرسالة ويمكن تحديدها كمراجَعة. احذف رسالة الاختبار من SQL Editor عند الانتهاء.

لا تمنح `anon` قراءة جدول الرسائل، ولا تضف سياسة عامة للقراءة. الترحيل يمنح الزوار إدراج الاسم والهاتف والنص فقط، ويمنع قراءة الرسائل وتعديلها وحذفها. المستخدمون المسجلون غير الموجودين في `feedback_admins` لا يرون الرسائل أيضًا. المسؤول المخوّل يقرأ الرسائل ويحدّث حالة المراجعة فقط، ولا يمكن لأي مستخدم إضافة نفسه إلى قائمة المسؤولين. لإلغاء صلاحية مسؤول، احذف صفه من `feedback_admins` عبر لوحة الخدمة؛ يطبق الإلغاء فورًا حتى قبل انتهاء جلسته.

تصل الرسائل إلى صندوق خاص داخل الموقع، ولا تُرسل رسائل بريد أو SMS تلقائيًا. بيانات الزوار لا تُحفظ في localStorage ولا تُعرض على الصفحة العامة. تسجيل الدخول القديم للشجرة لا يمنح صلاحية لصندوق الرسائل.

## التحقق المحلي من صلاحيات قاعدة البيانات

أُجريت اختبارات SQL فعلية في PostgreSQL عبر PGlite، في بيئة معزولة دون الاتصال ببيانات الإنتاج. لإعادة الاختبار دون إضافة اعتماد إلى التطبيق:

```sh
npm install --prefix work/feedback-db-check --no-audit --no-fund --package-lock=false @electric-sql/pglite@0.3.14
node --test tests/visitor-feedback.test.cjs tests/visitor-feedback-rls.test.cjs
```

يحاكي اختبار SQL أدوار Supabase و`auth.uid()`، ويتحقق من نجاح الإرسال، ومنع القراءة والتعديل والحذف للزوار، ومنع وصول الحسابات غير المخوّلة، وقراءة المسؤول وتحديث الحالة، ومنع ترقية الحساب ذاتيًا، ومن إلغاء الصلاحية فور حذف عضوية المسؤول. يبقى اختبار التشغيل على مشروع Supabase الفعلي لازمًا بعد تطبيق الترحيل لأن إعدادات Auth وData API تخص المشروع المستضاف.
